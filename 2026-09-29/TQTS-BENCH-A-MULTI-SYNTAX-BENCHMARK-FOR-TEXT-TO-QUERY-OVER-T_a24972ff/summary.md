# 论文速读：TQTS-BENCH-A-MULTI-SYNTAX-BENCHMARK-FOR-TEXT-TO-QUERY-OVER-TIME-SERIES-DATABASES

## 一句话总结
本文提出 **TQTS-BENCH**，一个面向时序数据库（TSDB）的多语法文本到查询基准测试，涵盖 97 个 TSDB、23 种查询语法、22 个应用领域和 4 类时间特定查询意图，并通过人审 AI 辅助工作流构建了 6,125 对高质量问答对，旨在填补现有关系数据库基准无法评估时序查询能力的空白。

## 研究问题与动机
- 现有文本到查询基准（如 Spider、BIRD）主要针对关系数据库（RDB），其查询语法统一为 SQL，而时序数据库（TSDB）具有异构的查询语法（如 Flux、PromQL、扩展 SQL 等），现有基准无法反映这一差异。
- 时序数据库的应用领域（如物联网、AIOps、云服务）高度依赖高频时间序列数据的连续采集与分析，现有基准在领域覆盖上存在局限，缺乏对时间密集型场景的支持。
- TSDB 查询涉及时间特定的意图（如窗口聚合、时间变化分析、时间定位、关系分析），而 RDB 查询主要关注与时间无关的操作（过滤、排序、聚合），导致现有方法在意图理解上存在不足。
- 缺乏系统性的 TSDB 文本到查询评估基准，使得研究者难以全面衡量大型语言模型（LLM）在该任务上的真实能力，也无法指导后续方法的改进。

## 核心贡献（创新点）
1. **提出 TQTS-BENCH 多语法基准测试**：涵盖 97 个 TSDB、23 种查询语法、22 个应用领域和 4 类时间特定查询意图，首次系统性评估 LLM 在时序数据库查询上的能力。  
   *与已有工作的本质区别*：现有基准（如 TEFD、PromCopilot）仅针对单一 TSDB 或查询语法，而 TQTS-BENCH 覆盖多语法、多领域、多意图，提供更全面的评估视角。

2. **设计人审 AI 辅助的构建工作流**：结合领域专家审核与可视化分析工具，通过查询意图识别、AI 生成候选问答对、人工验证与交叉校验，确保 6,125 对 QA 对的高质量与正确性。  
   *与已有工作的本质区别*：不同于纯自动生成的基准，该方法强调人工审核与专家参与，保证了时序数据库查询场景的真实性和可用性。

3. **揭示 LLM 和现有方法在 TSDB 查询上的性能瓶颈**：实验表明，即使最佳模型 Claude‑Opus‑5 也仅达到 48.98% 的执行准确率，远低于人类表现的 87.34%；现有 RDB 方法和 TSDB 方法均表现出较差的泛化能力。  
   *与已有工作的本质区别*：首次系统性地量化了 LLM 在时序查询任务上的差距，并分析了错误成因（语法异质性、意图误解、模式链接错误）。

4. **提供详细的错误分类与消融实验**：将错误划分为查询语法错误（75.29%）、意图理解错误（61.43%）和模式链接错误（17.09%），并通过将 TSDB 转换为 RDB 的消融实验证明语法多样性是性能低下主因。  
   *与已有工作的本质区别*：错误分析不仅停留在表面，而是深入时序查询特有的挑战，为后续方法改进指明了方向。

## 方法详解
- **基准构建流程**：
  1. **TSDB 收集**：基于 DB‑Engines 排名选择 23 个流行且易访问的 TSDB 管理系统，从官方文档、社区论坛和技术帖子中收集 427 个候选数据集和 1,405 个种子 QA 对。
  2. **数据筛选**：根据数据真实性与模式复杂度手动筛选出 97 个代表性数据集，并导入对应 TSDB 系统以实例化数据库环境。
  3. **查询意图识别**：与领域专家合作，从种子 QA 对中归纳出 9 类查询意图（4 类时间特定：I1‑I4；5 类时间无关：I5‑I9）。
  4. **人审 AI 辅助生成**：开发可视化分析工具，让标注员结合查询意图、数据库模式和上下文，使用 LLM（如 GPT‑5.6‑Sol）生成自然语言问题；标注员审核后，再用 LLM 生成可执行查询，形成候选 QA 对。
  5. **交叉验证**：两名标注员独立手写查询并执行，若结果一致且问题可答则通过，否则由仲裁员复审修改，最终得到 6,125 对验证 QA 对。

- **评估指标**：采用执行准确率（Execution Accuracy, EX），即预测查询的执行结果是否与预期答案匹配（考虑格式变换后的语义一致性）。

- **难度分级**：根据查询意图数量划分难易度（1‑3 意图为简单，4‑5 为中等，6‑9 为困难），以反映组合复杂度。

## 实验与结果
- **数据集**：TQTS‑BENCH 包含 6,125 对 QA 对，覆盖 97 个 TSDB、23 种查询语法、22 个应用领域，总数据量 41.68 GB。
- **评估基线**：
  - **LLM**：开源模型（Qwen3.8‑Flash、DeepSeek‑V4‑Pro、GLM‑5.3‑Flash、Kimi‑K3）与闭源模型（GPT‑6‑Sol、Claude‑Opus‑5、Gemini‑3.7‑Flash）。
  - **RDB 方法**：DeepEye‑SQL、OpenSearch‑SQL、RSL‑SQL、DAIL‑SQL、DIN‑SQL（均以 GPT‑4o‑mini 为骨干）。
  - **TSDB 方法**：PromCopilot。
- **主要结果**：
  - 最佳模型 **Claude‑Opus‑5** 取得整体 EX **48.98%**，人类基准为 **87.34%**。
  - 开源模型表现较差，如 DeepSeek‑V4‑Pro 仅 **22.51%**。
  - RDB 方法普遍极低（DeepEye‑SQL 5.83%、DAIL‑SQL 0.54%），表明方法难以迁移至 TSDB 场景。
  - TSDB 方法 PromCopilot 整体仅 **0.69%**，且在不同领域间泛化能力弱（目标领域 3.03% vs 其他领域 0.00%）。
- **提升幅度**：与现有基准（如 BIRD、Spider 2.0）相比，TQTS‑BENCH 对模型提出了更高挑战，当前最佳性能距离人类水平仍有约 **38 个百分点**的差距。

## 相关工作脉络
- **RDB 文本到查询基准**：Spider（Yu et al., 2018）、BIRD（Li et al., 2023）、Spider 2.0（Lei et al., 2025）等专注于关系数据库，共享 SQL 语法，未覆盖时序特有操作与异构语法。
- **TSDB 文本到查询基准**：TEFD（Wu et al., 2026）仅针对 InfluxDB 的 Flux 语法；PromCopilot（Zhang et al., 2026）聚焦 Prometheus 的 PromQL 查询，两者均局限于单一语法或领域。
- **定位差异**：TQTS‑BENCH 首次同时覆盖多语法、多领域、多意图，填补了系统性评估 LLM 时序查询能力的空白；其构建流程强调人工审核，保障了数据质量，优于此前纯自动生成的基准。
- **相关研究方法**：DeepEye‑SQL、DIN‑SQL 等 RDB 方法在查询生成环节依赖 SQL 语法约束，无法适应 TSDB 的异构语法；PromCopilot 依赖 Kubernetes 生态知识，泛化能力有限。

## 局限性与未来方向
- **基准规模与覆盖范围**：当前涵盖 97 个 TSDB，但 TSDB 生态系统仍在快速扩展，未来需纳入更多新兴系统（如高排名的 kdb+ 等）。
- **评估指标局限**：执行准确率（EX）依赖结果格式匹配，虽引入变换策略以减少误判，但仍未完全解决语义等价但格式不同的查询评估问题。
- **错误分析未穷尽**：当前错误分类主要基于语法、意图、模式链接三大类，实际错误可能涉及多类交织，需更细粒度的剖析。
- **未来方向**：
  1. 开发能自适应多语法的文本到查询模型，减少对单一 SQL 范式的依赖。
  2. 增强时间特定意图的理解能力，尤其是窗口聚合、变化分析等复杂操作。
  3. 优化大规模时序模式下的模式链接，克服“迷失在中间”现象。
  4. 探索跨领域泛化的 TSDB 查询方法，降低对特定应用场景（如 Kubernetes）的依赖。

## 研究启发与可借鉴点
- **人审 AI 辅助工作流**：结合自动化生成与人工审核的基准构建方法，可有效保障数据质量，尤其适用于需要领域知识的复杂场景（如时序数据库查询）。
- **多维度难度划分**：基于查询意图数量而非 token 长度评估难度，更贴合时序查询的组合复杂性，为其他领域基准设计提供参考。
- **错误驱动的分析框架**：将错误明确归类（语法、意图、链接），并辅以消融实验隔离变量（如转换 TSDB 为 RDB），可精准定位模型瓶颈，指导针对性改进。
- **跨基线对比设计**：同时评估 LLM、RDB 方法、TSDB 方法，全面揭示不同技术路线的局限性，为后续方法选择提供实证依据。
- **可迁移的创新机会**：本工作揭示的“语法异质性”和“时间意图理解”难题，可延伸至其他异构数据库系统（如图数据库、流数据库）的文本到查询研究。

## 关键术语表
- **TQTS‑BENCH**：一个面向时序数据库的多语法文本到查询基准测试，涵盖 97 个 TSDB、23 种语法、22 个领域和 4 类时间特定意图。
- **执行准确率（Execution Accuracy, EX）**：评估预测查询执行结果是否与预期答案语义匹配的指标。
- **时间特定查询意图**：与时序数据特性相关的查询需求，包括窗口聚合与重采样、时间变化分析、时间定位和关系分析。
- **模式链接（Schema Linking）**：将自然语言中的实体映射到数据库模式元素（如表、列、指标、标签）的过程。
- **Flux / PromQL**：InfluxDB 和 Prometheus 的查询语言，分别采用管道式语法和嵌套函数式语法，代表 TSDB 语法的异构性。
- **人审 AI 辅助工作流**：结合 LLM 生成候选数据与领域专家人工审核的基准构建方法，确保质量与真实性。
